# Changelog

🌐 **English** · [Français](docs/i18n/CHANGELOG.fr.md) · [日本語](docs/i18n/CHANGELOG.ja.md)

All notable changes to Kintai are documented here.

## [Unreleased]

### CI
- New `lint` job on every pull request: PHP and JavaScript syntax of the whole repository, JSON files (languages, `composer.json`, contract snapshot), `composer validate` and `composer audit`, and static analysis with PHPStan (level 0, `phpstan.neon`). The `crawl-smoke` job is removed: `crawl-bundles-smoke` runs the same crawl with the bundles installed.

### Fixed
- Dashboard wall mode: F5 (or Ctrl+R, F11, F12, Ctrl+L, Alt+←, dev-tools and view-source shortcuts) no longer bypasses the password. The lock now survives a page reload (salted hash in `sessionStorage`, never the password), the shortcuts are intercepted while the mode is active, leaving the page asks for confirmation, and Escape is locked in fullscreen when the browser supports it. Widgets are also inert in wall mode: no click, link, menu or keyboard focus, only the exit button answers.
- Dark theme: text on solid primary (orange), success, warning and danger buttons and badges is now dark instead of white, which was unreadable on the pale dark-theme colors (new `--color-on-primary/-success/-warning/-danger` tokens, white in the light theme).
- **Deleted, dismissed or deactivated staff no longer appear in the planning**: an anonymised account (or one removed from the database) stayed linked to its store and showed up under the shifts as a nameless `#90` whose employee page answered 404. The timeline, its print view and the monthly calendar now list only active, non-deleted members of the store.
- **Google Calendar and ICS feed showed shifts 9 hours late** (e.g. 06:00–15:00 appeared as 15:00–midnight in Tokyo). The store time zone field was free text and accepted values such as `UTC+9`, which is not a time zone for Google Calendar or PHP: events were placed in UTC. `StoreTimezone` now converts common spellings (`UTC+9` → `Asia/Tokyo`, `GMT-5`, `JST`…) and always yields a valid identifier; Google events and the ICS feed use it; the store form validates the field and suggests the valid identifiers.
- **Updating the site repairs the existing data and already-synced calendars**: the new migration `normalize_store_timezones` converts every store's time zone and resets the last reconciliation of each Google Calendar link, so the next `calendar-sync` run patches every event already sent (the content hash covers the time zone) instead of waiting up to 6 hours. No duplicate events, nothing to do for the employees.

### Added
- Dashboard wall mode now asks for a password: enabling it prompts for a password (typed twice, at least 4 characters), and leaving it (the "Exit wall mode" button, Escape or leaving full screen) asks for it again; cancelling keeps wall mode and restores full screen. The password lives only in the page's memory (never stored or sent) and resizing the window no longer exits wall mode. It is a guard against an accidental tap on a store screen, not a security boundary: the user's session remains the real access control.
- **Exports page** (`/exports`): any dataset of the application can be downloaded as an Excel workbook, CSV or JSON, for yourself, for chosen people, for a whole store or for all the stores you manage; the schedule can also be exported as ICS when it concerns one person in one store. Core datasets: schedule, employees (identity and contact only, never secrets), availabilities, shift types, stores and payroll estimate. Rights are decided per dataset and per store by the existing permissions (`shifts.view`, `employees.view`, `stores.view`, `payroll.export`); everyone can export their own schedule, employee record and availabilities. Each export is recorded in the audit log (`export.dataset`). CSV and workbook cells are neutralised against formula injection.
- **Bundle contract 1.30.0**: new extension point `Bundle::exportDatasets()` with `ExportDataset`, `ExportRowsProvider` and `ExportQuery`. A bundle declares its datasets (permission, columns, rows provider); the Core checks the rights and only hands the provider an already-authorised scope.
- **Download my schedule** (profile, "iCal" tab): an employee can fetch their own schedule for a store and a period (default: today to +90 days, capped at one year) as an ICS file for a calendar (with approved leave), a CSV for a spreadsheet (UTF-8 with BOM, ";" separator, formula-neutralised cells) or a JSON file. It is always the signed-in user's own schedule in a store they belong to, and each download is recorded in the audit log (\`export.schedule\`).
- **Shared "pick employees" component — contract 1.29**: `UserPicker` (`src/UI/Components/UserPicker.php`, fluent like `Form` or `Table`, `public/assets/js/modules/user-picker.js` for "select all" and the counter, no inline script or style) and `UserSelection` (`src/Core/Services/UserSelection.php`: `candidates()` lists the active members of a store, optionally only those holding a permission; `resolve()` re-reads a saved selection; `validate()` refuses unknown accounts, duplicates, too many or none). A selection stores account ids, never addresses: an address change is followed and a deactivated or removed account is dropped. Both are exposed to bundles as `kintai\Contract\View\Components\UserPicker` and `kintai\Contract\Services\UserSelection` (contract snapshot regenerated), and meant for any screen that needs to choose people. The picker shows the chosen people as removable chips with a search field to add the others (the checkbox list stays as the no-JavaScript fallback), and the instance Owners are always offered, tagged "Owner", even when they belong to no store. Texts in fr, en and ja; `UserSelectionTest`, `UserPickerTest`.
- **Bundle translations — `perm_category_{category}` is a reserved key** (`TranslationContractChecker`, `src/Contract/translation-keys.php`): like `notif_`, `audit_` and `cron_job_`, a bundle may name the label of its permission category `perm_category_{category}` without its slug prefix, because the Core roles page builds that key from the category, a permission key stored in the database (`open_shifts`, `swaps`…) that cannot follow the slug. Test case added.
- **E-mails — one sender address, set by the Owner** (Owner settings › General): the sender address and name of every e-mail Kintai sends (daily reports, planning checks, notifications, password reset, mail test) are now one setting, no longer a line of `config/mail.php` or an environment variable to edit on the server. Empty keeps the configuration file; an invalid address is refused and nothing is saved. Bundles need no change: they all send through the Core mailer. Texts in fr, en and ja; `MailSenderSettingTest`.
- **Storage warning banner (Owner only).** When the server's free disk space falls under 1 GB or under 10 % of the disk, a banner at the top of every page tells the Owner — and nobody else — that storage is running low, with the free space, the total and the space taken by backups, and a **Manage backups** link. Same style as the maintenance and password banners; it disappears by itself once space is freed. It only informs: nothing is deleted or blocked, and the measure is cached for five minutes. New `StorageUsageService`.
- **Activity log — manual purge by the Owner** (Activity log page): a **Purge the log** box, visible to the Owner only, deletes the entries older than 7, 30, 90, 180 or 365 days, or everything, after a confirmation. Disk space is given back right away (`VACUUM` on SQLite, `OPTIMIZE TABLE` on MySQL), which frees space and speeds the page up; the number of deleted entries is shown, and the purge itself is recorded in the log. The automatic retention (Owner settings) is unchanged. `POST /admin/activity/purge`, Owner-only; texts in fr, en and ja; `ActivityLogPurgeTest`.
- **Scheduling — warning when the employee is unavailable that day.** When an employee has marked a weekday as unavailable in **Profile › Availability**, creating a shift for them on such a day (form, quick creation from the timeline) or moving or reassigning one onto it (edit form, drag and drop) now shows a red box instead of saving: "Aiko marked Sunday as unavailable (2026-08-02). Schedule this shift anyway?". Two buttons: **Cancel** (the main action) and **Force the schedule**, which saves anyway. It is a warning, never a block, and nothing is said for an employee who never filled in their availability or when only the hours of an existing shift change. New `AvailabilityGuard` service; the JSON endpoints `POST /admin/shifts/quick` and `POST /admin/shifts/{id}/move` answer `409` with `code: availability_conflict` unless the body carries `force_availability`.
- Wiki — new structure by audience (Getting Started, Employee Guide, Manager Guide, Administration, Installation & Operations, Developers, Project) and 23 new pages in English, French and Japanese: quick tour, glossary, FAQ, profile, dashboard, notifications, calendars (iCal and Google Calendar, with the Google Cloud setup for Owners), installable app, bundles and catalogue, setup wizard, scheduled tasks, e-mail and push setup, troubleshooting, bundle contract and the full bundle-creation guide (moved from `docs/`). The side-bar groups are translated by the app (`docs_group_employee`, `_manager`, `_admin`, `_operations`, `_developers`, `_project`). `php scripts/check-wiki.php <folder>` checks a wiki before publishing it: every side-bar page exists in the three languages, the language line is present, internal links and images resolve.
- **Notifications — quiet hours no longer hold anything back** (Quiet hours): during a user's quiet hours the push is still sent, flagged `quiet`, and shown without sound or vibration — the service worker sets `silent`, FCM goes to low priority (Android channel `kintai_quiet` for the future mobile app, APNs priority 5). E-mails are no longer held back either: an e-mail does not wake anyone. So there is nothing to replay and no cron job is needed, which matters on a plain Apache server. Whether the notification is really silent depends on the browser or device (`silent` is not honoured everywhere). The notification test of the Owner is never flagged quiet.
- Table rows designated by a notification: the class `tr--highlight` on a `.data-table` row (`?highlight={id}`) gives it a tinted background and a left bar, for the bundles whose notifications target a list rather than a detail page.
- Bundle contract 1.23 — notification types and automatic "read" (last core lot of the notification overhaul): `Bundle::notificationTypes()` accepts, besides `type => icon`, the enriched format `['icon', 'category', 'channels' => ['push', 'email'], 'reference_type']` (category and channel defaults of the user preferences; invalid declarations are ignored and logged), and `NotificationService::markReadFor(userId, referenceType, id|ids)` lets a bundle's detail page mark the notifications of the object just opened as read (never throws). The Core already handled both since lots L2 and L3; this release documents them (`docs/creating-a-bundle.md`, fr/ja) and raises `Contract::VERSION`. Each official bundle then migrates in its own PR.
- **Notifications — purge and Owner settings** (lot L7 of the overhaul): the scheduled job `notification-purge` (a name reserved to the Core, `php scripts/cron.php` or `/cron/run/notification-purge`) deletes, in batches of 1,000, the **read** notifications older than the retention delay (90 days by default, 7 at minimum) — an unread notification is never deleted — and the web push subscriptions no send has touched for 180 days (dead addresses the push service never reported as expired). New **Settings › Notifications** page (Owner, `/admin/notifications-settings`): the retention delay, the **state of each channel** (bell, browser push with missing extensions / keys / number of subscribers, e-mail configured or not and public URL, mobile FCM push), a **"Send me a test notification"** button that goes through every active channel regardless of preferences and quiet hours (and tells which ones it left through), and **regeneration of the browser push keys** with confirmation (every current subscription becomes invalid, each browser subscribes again on its next visit). The `notification_test` type does not appear in the users' preferences.
- **Notifications — e-mail channel** (lot L6 of the overhaul): a notification can also arrive by e-mail, according to the "E-mail" column of the profile preferences. By default e-mail is on only for the decisions that touch the employee's schedule (shift assigned, shift deleted); the user turns on the rest. `NotificationMailer` sends immediately, in the recipient's language: subject `[Kintai] {type label}`, the notification text, a "View" button to `/notifications/{id}/open` (sign-in required) and a one-click unsubscribe link for that type. Same rule as push (type preference, quiet hours); a failure is logged and blocks neither the action nor the other channels; the SMTP connection timeout is 5 s (instead of 30) during the request of the user who triggers the notification. With no e-mail configured on the instance (`MailerService::isConfigured()`) or no public URL (links must be absolute), nothing is sent and the profile says so. **Unsubscribe**: `GET /notifications/unsubscribe?u=&t=&c=&s=` shows a confirmation (merely displaying it never unsubscribes: antivirus software and mail previews open links), `POST` unsubscribes; the address is signed by HMAC (user, type, channel) with an instance secret created on first need (`app_settings.instance_secret`), and the `List-Unsubscribe` / `List-Unsubscribe-Post` header (RFC 8058) allows one-click unsubscribing from the mail client; this one address is exempt from the CSRF token (no session). Mail transports accept extra headers (`MailHeaders` drops any name or value containing a line break); `MailerService` gains `isConfigured()` and an injectable transport for tests.
- **Notifications — native web push (VAPID), without Firebase** (lot L5 of the overhaul): browsers and the PWA receive their notifications directly through the Web Push protocol, with no Firebase project or setup. The instance's VAPID keys are created automatically (install, or migration for an existing instance) and kept in `app_settings`; only the public key is given to the browser. New `WebPushService` (`minishlink/web-push` library, with `guzzlehttp/guzzle` as HTTP client): `aes128gcm` encrypted payload (required by Safari), 24 h TTL, an expired subscription (404 / 410) is deleted, any other error is logged without retry and never blocks the action or the other channels. It follows the same rules as mobile push (type preference, quiet hours). New `web_push_subscriptions` table; the old "web" tokens of `device_push_tokens`, which could never work, are deleted (`device_push_tokens` now only serves FCM for the mobile app: the `push-tokens` API no longer accepts `web`). `push.js` is rewritten: loaded on every signed-in page, it sends the browser's subscription back to the server at each load (rotation, lost subscription, browser shared between two accounts), shows "enabled" only after the server's positive answer, replaces any subscription made with old keys, and reports the special cases (permission denied, unsupported browser, iPhone/iPad outside an installed PWA). Signing out deletes this browser's subscription. The service worker reads the new format and subscribes again on `pushsubscriptionchange`. A subscription's address is checked before it is saved (HTTPS, public domain name, resolving to a non-private address): otherwise a user could make the server send requests to the internal network. `config/openssl.cnf` is the fallback for PHP installs without an `openssl.cnf` (mostly Windows), where key creation failed. `config/push.php` loses the `fcm.web` section and `.env.example` the `PUSH_FCM_WEB_*` variables; the `curl`, `openssl` and `mbstring` extensions are required for web push, which reports itself unavailable if they are missing.
- **Notifications — preferences by type and channel, quiet hours** (lot L4 of the overhaul): the profile's "Push" tab becomes "Notifications" (the old `?tab=push` link leads there) with three cards — the state of this device, the preference grid (one row per active type, grouped by category, Push and E-mail columns with "enable / disable all", the bell shown checked and greyed because it is never turned off) and the quiet hours (start, end, a range that may cross midnight, instance time). New `notification_preferences` table that keeps only the deviations from the type's defaults, and `users.quiet_hours_start` / `quiet_hours_end` columns; `NotificationPreferenceService` is the entry point. `NotificationService::notify()` now sends push only if the type allows it for that recipient (the bell always receives everything; during the user's quiet hours the push is still sent, silently — see "Quiet hours" below), and `notifyMany()` loads the preferences of all recipients in one query. A deleted account's preferences are deleted with it. API: `GET|PUT /api/v1/users/{user_id}/notification-preferences` (oneself or `employees.update`), see `.wiki/API-Reference.md`. E-mail and native web push sending arrive in the next lots: the E-mail column already records the choice.
- **Notifications — precise links and automatic "read"** (lot L3 of the overhaul): opening the planning day view marks as read the notifications of the user's shifts shown (`NotificationService::markReadFor()`, `NotificationRepositoryInterface::markReadByReference()`, already tied to their object type by the registry); the link of an assigned or updated shift carries `&highlight={id}` and the shift's bar is outlined in the day view. A deleted shift keeps the link to the day. A failure of the "read" step never blocks the page from displaying.
- **Notifications — single type registry** (lot L2 of the overhaul): `NotificationTypeRegistry` gathers the types of the Core and of the active bundles, each with its icon, its preference category (`planning`, `requests`, `messages`, `reports`, `system`), its default channels (push, e-mail) and the type of object it designates. `Bundle::notificationTypes()` accepts, besides the old `type => icon` format, an enriched format `['icon', 'category', 'channels', 'reference_type']` (`kintai\Contract\Extension\NotificationType`); an invalid declaration is ignored and logged, and a Core type cannot be redefined. `NotificationService::notify()` writes `reference_type` from the registry (the basis of the automatic "read" on visit, next lot). The contract version number (1.23) changes with the bundles lot.
- **CI — soumission des formulaires** (`crawl-smoke.php --forms`, job `crawl-forms-smoke`) : en plus du parcours, chaque formulaire POST rencontré est soumis une fois avec des valeurs plausibles ; 4xx accepté, 5xx ou erreur PHP en échec. Actions destructrices de l'instance de test ignorées. A déjà trouvé le code employé en doublon qui donnait une erreur 500.
- **CI — parcours des pages avec les 12 bundles officiels** (`scripts/ci/crawl-bundles-smoke-test.sh`, job `crawl-bundles-smoke`) : chaque bundle est cloné depuis sa branche `develop` (`BUNDLES_REF`), installé avec le vrai `BundleInstallerService` (`scripts/ci/install-bundle-archive.php`), tous activés, puis le même parcours qu'en `crawl-smoke`. Premier passage local : 254 pages, aucune erreur.
- **CI — parcours des pages d'une instance neuve** (`scripts/ci/crawl-smoke-test.sh`, job `crawl-smoke`) : installation de démonstration, puis suite des liens internes en tant que propriétaire, gérant et employé ; échec sur toute page 5xx ou affichant une erreur PHP. Ce filet manquait : les tests unitaires simulent les dépôts et ne voient pas un décalage entre code, vue et schéma.
- - Bundle contract 1.22 — view helpers `style_class()` and `inline_styles()`: a value only known at render time (a user colour, a bar height, a percentage) becomes a class whose rule is emitted in a single `<style nonce>` by the layout (or by `inline_styles()` on a page without layout), instead of a `style="…"` attribute. Values are filtered so user data cannot escape the rule. First step towards dropping `'unsafe-inline'` from the CSP `style-src`; see "Dynamic styles" in `docs/creating-a-bundle.md`.
- Bundle contract 1.21: `kintai\Contract\Auth\UserAnonymizer` joins the stable surface, so a bundle that deletes an account anonymises it exactly like the employee page and the API do (personal data erased, account deactivated, rights and tokens revoked, history kept under "Deleted user"). Used by resignation-report.
- Languages — instance language chosen by the Owner. The web installer asks for it and the instance settings change it; it is saved in the environment file (`APP_LOCALE` in `.env`, or the env file actually loaded) and is the language of every text for users who have not chosen their own. Display language is now: signed in, the profile language, otherwise the instance language (the browser language no longer overrides it); on the login page, the language picked with the new language selector, then the language of the last account signed in on this browser (cookie `kintai_locale`, kept after sign-out), then the browser language, then the instance language. The profile offers "Instance language" (stored as an empty `users.language`), now the default for new accounts; existing accounts keep their language. An existing instance without `APP_LOCALE` keeps the language marked as default in `lang/languages.json`. Notifications, iCal feeds and password-reset e-mails follow the same rule (they used to fall back to French), and `php scripts/cron.php` uses the instance language. The Languages page no longer has "Set as default" (the instance language can be neither disabled nor deleted there).
- Bundle contract 1.20 — scheduled job labels by translation convention: `php scripts/cron.php` lists each job with the translation `cron_job_{name}` (dashes turned into underscores, e.g. `cron_job_auto_validate`) found in the Core's or the bundle's `lang/` files, or its name when there is none. The Core's own jobs (`backup`, `log-purge`, `license-check`) are now translated (fr/en/ja) instead of two hardcoded French labels and a bare `license-check`. The command-line script now uses the instance's default language (it had none outside an HTTP request, so every label stayed untranslated).
- Dashboards — movable widgets, saved per user. On both the manager and the employee dashboards, "Customize" now switches to an edit mode: every widget gets a toolbar to drag it by its ⠿ handle, move it up or down with arrows (touch screens, keyboard) and switch it between half and full width — two half-width widgets sit side by side, with the same height. Every change is saved right away; "Reset layout" goes back to the default (Core widgets first, then bundle widgets, Finances and HR side by side). A widget that is hidden (turned off, missing permission, bundle disabled) keeps its place. The API returns and accepts the layout too: `GET/PUT /api/v1/users/{user_id}/dashboard-prefs` gain a `layout` field (`{order, widths}`, `null` = default); `widgets` and `layout` are each saved only when sent. New column `user_dashboard_prefs.layout`. The "Customize" button also opens its panel on the first click again (it took two).
- Installation — after the web installer, the Owner is now signed in and taken to a setup assistant (`/admin/setup`): license first (optional; without one, the free plan allows 4 active bundles), then the bundles to install, limited by the license, downloaded from the official catalogue on the Core's update channel and enabled. A bundle that cannot be installed (no Internet access, incompatible version) does not block the installation: it is listed to retry from the catalogue. Until the assistant is finished or skipped, the Owner sees a "Finish setup" banner. A fresh install starts with no active bundle instead of all twelve (which ignored the free-plan quota); `scripts/provision.php` does the same. Existing instances are not affected.
- Scheduled jobs from the command line — `php scripts/cron.php {job}` runs any scheduled job, the Core's and those of active bundles (`auto-validate`, `photo-retention`, `backup`, `log-purge`…), without a token, for a server with SSH access and a local crontab; `php scripts/cron.php` lists the available jobs, and URL parameters become `--key=value` (e.g. `php scripts/cron.php auto-validate --date=2026-10-13 --all=1`). Shared hosting without SSH keeps calling `/cron/run/{job}` with a cron token from the host's scheduled tasks. The script boots exactly like the web front controller: the `.env` loader moved to a shared helper (`kintai_load_env_file()`, also used by `public/index.php`), and the installed bundles' classes are registered, without which no bundle job would be available on the command line.
- Bundle contract 1.12 — new extension point `Bundle::profileSections()` and value object `kintai\Contract\Extension\ProfileSection` (step 4 of the bundle contract plan, first piece of the team-directory extraction): a bundle adds a section to the "My information" form of the profile (its own view, rendered with the signed-in user) and declares the checkboxes of the `users` table that section saves, limited to the columns the Core opens to bundles (`ProfileSections::WRITABLE_USER_COLUMNS`: directory visibility and contact sharing). `profile.php` and `AuthController` no longer name `team-directory`: the directory checkboxes moved to `auth/_profile_directory.php`, shown by `kintai\Core\Extension\ProfileSections` as a fallback until the bundle declares its own section. Saving the profile now writes only the checkboxes of the sections shown, so those of a disabled bundle keep their value even in a hand-crafted request.
- Bundle contract 1.11 — attendance provider (step 3c of the bundle contract plan): `Bundle::attendanceProviders()`, interface `kintai\Contract\Provider\AttendanceProvider` and value object `Attendance`. The dashboards (clocked-in now, late arrivals, the employee's open clock-in) and the "Alerts" widget now read clock-ins through `kintai\Core\Extension\Attendances` instead of the clock-in table; until a bundle declares a provider, the Core keeps reading that table (unchanged behaviour, including when `timeclock` is disabled).
- Bundle contract 1.10 — absence provider (step 3b of the bundle contract plan): `Bundle::absenceProviders()`, interface `kintai\Contract\Provider\AbsenceProvider` and value object `Absence`. Schedule conflicts, the schedule's absence display, the iCal feed and store statistics now read absences through `kintai\Core\Extension\Absences` instead of the leave table; until a bundle declares a provider, the Core keeps reading that table (unchanged behaviour, including when `timeoff` is disabled).
- Bundle contract 1.9 — first provider (step 3 of the bundle contract plan): `Bundle::pendingRequestsProviders()`, interface `kintai\Contract\Provider\PendingRequestsProvider` and value object `PendingRequest`. The "Requests" page and the dashboard's "Pending requests" counter now read pending requests through providers (`kintai\Core\Extension\PendingRequests`) instead of the leave, swap and open-shift tables: the page is built generically (one section per provider, typed columns) and the Core keeps its own providers for `timeoff`, `shift-swap` and `shift-claim` until they declare theirs. Pages unchanged (compared before/after). The counter now follows the same permissions as the "Requests" page.
- Bundle contract 1.8 — new extension point `Bundle::cronJobs()` and contract interface `kintai\Contract\Cron\CronJob` (step 2j of the bundle contract plan, last extension point of step 2): a bundle ships scheduled jobs run through `/cron/run/{name}` with an Owner-issued cron token, instead of the Core registering them itself. Core job names are reserved and each job is isolated; `auto-validate` (daily reports) stays registered by the Core until `daily-report` declares its own.
- Bundle contract 1.7 — new extension point `Bundle::notificationTypes()` (type => icon) and label conventions (step 2i of the bundle contract plan): a notification type's label is the translation `notif_{type}`, an activity log action's label is `audit_{action}`, both found in the bundle's own `lang/` files — so a new bundle no longer needs the Core to list its notifications or audit actions (`notification_type_catalog()`, activity log). New helpers `translation_or()` and `audit_action_label()`. Notifications of a disabled bundle keep their translated label.
- Bundle contract 1.6 — new extension point `Bundle::actions()` and value object `kintai\Contract\Extension\Action` (step 2h of the bundle contract plan): a bundle adds links to named slots of Core pages — staff list row menu, "Reports" card of the employee form, store employee report (header and rows), employee schedule toolbar — instead of those views naming `salary-report` and `shift-swap` themselves. New `kintai\Core\Extension\Actions`; the historical links stay until their bundle declares its own (pages compared before/after: identical).
- Bundle contract 1.5 — new extension point `Bundle::viewVariables()` (step 2g of the bundle contract plan): a bundle shares values with every view of authenticated pages (`name => fn(array $user): mixed`), e.g. the counter shown as a navigation badge. One Core middleware, `BundleViewDataMiddleware`, replaces `DailyReportNavMiddleware` and `MessageCountMiddleware`, which computed bundle data in the Core on every page: it shares `managed_store_ids` (Core), the variables declared by active bundles (Core names refused, each one isolated) and, until `messaging` and `daily-report` declare theirs, `unread_messages_count` and `daily_report_staff_stores` as before. Navigation unchanged (rendered HTML compared before/after).
- Bundle contract 1.4 — new extension point `Bundle::dashboardWidgets()` and value object `kintai\Contract\Extension\DashboardWidget` (step 2f of the bundle contract plan): a bundle adds widgets to the manager or employee dashboard (its own view and data function, permission, per-store feature); they appear in the "Customize" panel and after the Core's widgets, each one isolated (an exception removes that widget only, logged). New `kintai\Core\Extension\DashboardWidgets`. The widgets the Core renders for bundles today (pending leave and swap requests, clock-ins, team notes) stay until their bundle declares its own; a bundle may reuse their keys to keep users' choices. Saving the dashboard preferences keeps the widgets of bundles disabled at that moment. Dashboards are unchanged today (rendered HTML compared before/after).
- Bundle contract 1.3 — new extension point `Bundle::storeFeatures()` and value object `kintai\Contract\Extension\StoreFeature` (step 2e of the bundle contract plan): a bundle declares the features a store can switch on or off, and the "Features" card of the store form offers them while it is active, instead of the Core listing every bundle's features by hand (`_form-store.php`, `AdminStoreController`). New `kintai\Core\Extension\StoreFeatures` (Core features, declared ones, historical fallback for bundles that don't declare anything yet — the store form is unchanged today); `feat_bundle()` now relies on it and `FeatureManager::STORE_FEATURE_BUNDLE_MAP` is deprecated. Saving a store keeps every stored feature that isn't offered at that moment (bundle disabled instance-wide), including features of bundles the Core doesn't know. The form now follows whether a bundle is actually loaded (like the navigation), not only its stored on/off setting: a bundle switched on but missing or incompatible no longer shows a card that leads nowhere.
- Bundle contract 1.2 — new extension point `Bundle::permissions()` (step 2d of the bundle contract plan): a bundle declares its permission categories (`category => actions`) and the Roles page offers them while it is active, instead of the Core listing every bundle's categories by hand. Core categories (`employees`, `shifts`, `stores`, `payroll`) can't be redefined; malformed or duplicate categories are ignored and logged. - Data — deleting an account no longer depends on the database driver (audit of 2026-10-13, M8). An admin deletion (web and API) erased the `users` row: under MySQL the foreign keys cascaded and wiped the person's shifts, clock-ins, leave, messages and reports (payroll history lost), under SQLite everything stayed orphaned. Every deletion — admin, API or self-service — now goes through the new `UserAnonymizer`: personal data and avatar erased, account inactive with `deleted_at` set, roles and tokens revoked, history kept under "Utilisateur supprimé". Deleted accounts no longer appear in the user list, its exports and `GET /api/v1/users`. The self-deletion no longer sets the NOT NULL `language` column to null (refused by strict MySQL). Migration `2026_10_16_000000_mark_anonymized_users_as_deleted` sets `deleted_at` on accounts anonymized earlier.
- Data — deleting a store is now a soft delete on both database drivers (audit of 2026-10-13, M8). It erased the `stores` row: under MySQL the foreign keys cascaded and wiped the store's shifts, clock-ins and reports, under SQLite they stayed orphaned. The store now gets `deleted_at`, becomes inactive and releases its code (renamed `DEL-{id}-{code}`, so a new store can reuse it and code login stops matching it) and URL aliases; its history stays in the database. `StoreRepositoryInterface::findAll()` and `findByCode()` skip deleted stores (lists, selectors, bundles), the new `findAllWithDeleted()` keeps the names of past shifts' stores, a URL to a deleted store answers 404, role assignments scoped to it are revoked, and `DELETE /api/v1/stores/{id}` now goes through `StoreService` like the web form.
- Data — foreign keys are now enforced under SQLite too (audit of 2026-10-13, M8): the SQLite connection enables `foreign_key_constraints`, so `onDelete` rules (cascade, set null, restrict) behave as under MySQL instead of silently leaving orphaned rows. Migration `2026_10_16_000001_repair_orphans_for_sqlite_foreign_keys` repairs existing databases first: accounts and stores that no longer exist but are still referenced are recreated as already-deleted placeholders with the same id ("Utilisateur supprimé", "Magasin supprimé #id"), so their history (shifts, clock-ins, payroll) is kept; other orphans follow their key's rule. Migrations (Core and bundles) and the factory reset run with SQLite foreign keys suspended (`SqliteForeignKeys`), since altering a table rebuilds it under SQLite and would otherwise trigger cascades.
- i18n — raw translation keys shown on screen: `year`, `all_months` and `all_years` (used by the hiring and resignation report filters but only shipped by the salary-report bundle) now live in the Core `lang/*.json`, and `role_add_holders_hint` was missing in Japanese. A new test checks that every locale in `lang/` carries the same keys (a language added later is covered automatically) and that every literal `__('key')` used in `src/` exists.
- API — `POST /api/v1/auth/login` answered 500 on every fresh install: the `api_tokens.expires_at` column, written by the login and read by `ApiAuthMiddleware`, existed in no migration (only in databases inherited from an old schema). A migration adds it, and the CI provisioning smoke test now logs in through the API and calls `/api/v1/auth/me` with the token.
- Security — the instance could be left without an administrator: an Owner could delete themselves (`DELETE /api/v1/users/{id}` included), deactivate themselves, or drop the Owner role from the last Owner. New `OwnerGuard` (`src/Core/Auth/OwnerGuard.php`): there is always at least one active Owner, and an Owner can neither delete, deactivate nor demote their own account (another Owner can do it, as long as one remains). It applies to the web user form and deletion, the API (`PUT`/`DELETE /api/v1/users/{id}`) and the removal of the Owner role from `/admin/roles`; the self-service account deletion is refused for an Owner.
- Two admin pages answered 500. The store statistics page (`/admin/stores/{id}/stats`) divided by zero when every employee of the period had worked 0 h; and the per-member deductions form (`/admin/stores/{id}/members/{mid}/deductions`) called `Form::start()`, a method the `Form` component no longer has (and posted without a CSRF token). Both now render, and a regression test renders the real views.
- Subfolder installs — 19 redirections (17 in the backup/update controller, 2 in the notifications controller) were written `Response::redirect('/admin/…')` and ignored the install prefix: under `https://host/Kintai/` the update, backup and notification screens sent users to the domain root (404). They now go through `$this->base()`, and a test forbids any controller redirect to an absolute path without that prefix.
- Security — a shift type enabled on several stores could be edited or deleted by the manager of just one of them, changing the shifts and the payroll of the others. Editing or deleting a shared type (web and `PUT`/`DELETE /api/v1/shift-types/{id}`) now requires managing every store it is enabled on, or having no store restriction; a manager can still enable or disable the type for their own store. A type used by a single store is unchanged.
- Robustness — an enabled bundle with a missing table (typically after an update whose migration was not run) made the whole dashboard answer 500 for everybody. The data of bundle widgets (team notes on the admin and employee dashboards, pending open-shift claims on the dashboard and on the requests page) is now loaded through `WidgetGuard`: a failing widget disappears, the error is logged, and the rest of the page renders.
- Demo data — `php scripts/provision.php --seed` (and the "demo data" box of the web installer) failed on a current schema: the SQL files in `database/seeds/` were frozen on the first versions (`stores.break_settings`, dropped since, made them fail) and nothing tested them. They are replaced by `DemoDataSeeder`, written through the Eloquent models (so independent of the driver and of the schema): 2 stores, 3 shift types enabled on both, 2 managers, 4 employees (one in both stores) and two weeks of schedule, password `Demo1234!`, idempotent. Only Core tables are seeded; bundle data belongs to each bundle. The CI provisioning smoke test now installs with `--seed` and checks the result.
- Security — stored HTML/CSS injection through colours (audit of 2026-10-13, M1): the colour of an account, a shift type or a role was saved as typed and ended up in `style=""` attributes (`red;position:fixed;…`). The new `ColorRule` accepts only `#RGB` / `#RRGGBB`: forged values are now refused (422) by the web forms (`AdminUserController`, `AdminShiftTypeController`, `AdminRoleController`) and the API (`POST`/`PUT /api/v1/users` and `/api/v1/shift-types`). As a second layer, the `HexColor` cast on the `User`, `ShiftType` and `Role` models replaces an invalid stored colour with the default one at read time (so views and bundles never see it), and the `2026_10_15_000000_sanitize_stored_colors` migration cleans what is already in the database. New `safe_color()` helper and `error_invalid_color` message (fr/en/ja).
- API — tokens no longer live forever (audit of 2026-10-13, M9): a token issued by `POST /api/v1/auth/login` without `expires_in` now expires after 90 days (`AuthController::TOKEN_TTL`), a longer `expires_in` is capped at 90 days, and an invalid one (zero, negative, not an integer) is refused with `422 INVALID_EXPIRES_IN` without counting as a failed login. The `2026_10_15_000001_expire_api_tokens_without_expiry` migration gives existing tokens without expiry a 90-day deadline.
- API — every token-authenticated request answered `401 MISSING_TOKEN` under Apache: Apache does not pass the `Authorization` header to PHP's `$_SERVER` (mod_php, and CGI/FastCGI without extra configuration). `public/.htaccess` now forwards it as an environment variable and `Request::withAuthorizationHeader()` recovers it from `REDIRECT_HTTP_AUTHORIZATION` or the raw headers (`getallheaders()`), without overriding a value the server already provides (`php -S`, Nginx). Found while testing the audit of 2026-10-13 on a XAMPP instance.
- API — request bodies are now validated (audit of 2026-10-13, M9). Write endpoints passed the JSON body straight to the repository: `POST /api/v1/users` or `/users/{id}/rates` with an empty body answered 500 (SQL constraint), `PUT /api/v1/stores/{id}` with `{}` was accepted, any column could be written (`deleted_at`, `created_by`, computed shift fields…), a rate could target a missing shift type, and a shift created through the API lacked its computed fields. New `PayloadValidator` (whitelist, types, formats, ranges, `422` with one message per field) and `ApiPayloadRules` (one rule set per resource) applied to users, stores (update), shift types, shifts, availabilities, user rates and dashboard/navigation preferences. Shift `duration_minutes`, `cross_midnight`, `starts_at`, `ends_at` are computed server-side; duplicate e-mails, employee numbers and store codes are refused with `422`; an update that changes nothing is refused.
- Security — hardening from the audit of 2026-10-13 (round 2): the bundle installer now validates `slug` and `version` before building any disk path (a slug such as `../..` moved the staging directory outside `storage/bundles`); `POST /notifications/{id}/read` only redirects to an internal path (open redirect); the "report an issue" modal only links to a real GitHub issue URL and no longer crashes every page on `?ri_success[]=x`; the iCal feed of a deactivated account or of an employee who left the store is no longer served; push-token unsubscription only removes the logged-in user's own device.
- Bundles audit 2026-10-13 (fixtures and tests; the fixes themselves live in the bundles' repositories): shift-swap — approving an already accepted swap swapped the shifts back, and approve/refuse/delete ignored the request status and the current owners of the shifts; timeoff — approve/refuse ignored the request status, dates were not validated and the store was always the employee's first one; notebook — "whole organisation" notes could be edited by a single-store manager. The anonymous-feedback hint no longer claims the identity is invisible to managers: it stays in the activity log.
- Staff reports (hiring / resignation / salary) — two fixes in the shared `HasStaffReportCrud` trait, found by the audit of 2026-10-13. A non-Owner holding the permission without any store restriction (custom role set to "All stores") got an empty store list and a 403 as soon as they filtered by store on the "all reports" pages (the test looked at `is_admin` instead of `managed_store_ids === null`). Editing a report also accepted any `user_id`: the employee must now be a member of the report's store.
- Security — store member management (`/admin/stores/{id}/members*`, permission `employees.update`) let a store manager assign any non-system role, including to themselves: a role carrying "All stores" permissions then granted rights on every store. `PermissionService::canAssignRole()` now caps the assignable roles to the caller's own permissions (and requires an unrestricted grant for the role's "All stores" keys). Adding, changing or removing a member also checks that the target account exists and that only an Owner can act on an Owner account.
- **API — `POST /api/v1/stores/{store_id}/members` accepted any body field** — an `id` in the body overwrote a membership of another store, `user_id` was not checked (orphan or duplicate rows) and `PUT` could reassign a membership to someone else. The controller now uses a field allow-list, ignores `id`/`store_id`/`role`/`is_manager`, requires an existing non-member `user_id` on creation and keeps `user_id` immutable on update.
- **Release — v0.3.4 tag created but no GitHub Release published** — `[Unreleased]` had accumulated every entry since v0.1.1 (~129,000 characters) and GitHub rejects a Release body over 125,000 (`HTTP 422: body is too long`), after the workflow had already pushed the tag. `release.yml` now truncates the notes at the last whole line under 120,000 bytes and links to the full `CHANGELOG.md`, and what was already published is archived under a dated section so `[Unreleased]` only carries what is new. See `docs/releasing.md`.
- Notifications — the notification of a deleted shift is now marked read when the employee views that day in the planning. It used to designate the shift itself, which no longer exists and so could never be "seen": it now designates the day (`reference_type` `shift_day`, `shift_day_reference()`).

### Added
- Readable URLs — web pages no longer show database ids for stores and employees: `/admin/stores/3/edit` becomes `/admin/stores/所沢東町店/edit` (or an optional romaji slug the Owner types on the store form, e.g. `tokorozawa-higashicho`), and `/admin/users/18/edit` becomes `/admin/users/016/edit` (the employee number, never the name — personal data that would end up in server logs and the `Referer` header; `id-42` for an employee without a number). The extra fields come from the License Manager server's `activate`/`validate` API, which previously only returned `type`/`expires_at` even though `issued_at`/`max_activations`/seat count were already on the `licenses`/`activations` tables — its `LicenseController` now includes them in both responses, and `LicenseClientService::applyResult()` persists them into the same `app_settings`-backed local state (carried forward, like `type`/`expires_at`, through the offline grace period when the server is unreachable). - Licensing — the freemium model gains actual plan tiers: a paid license now carries its own limits (`max_stores`/`max_employees`/`max_bundles`, a free-form JSON map since other Freemium products built on the same License Manager have their own dimensions) instead of any valid license meaning unlimited. `PlanLimitService::maxStores()`/`maxEmployees()`/`maxActiveBundles()` read these from `LicenseClientService::entitlements()` — a key missing from a license's `limits` map (or an explicit `null`) means unlimited for that dimension specifically; a paid license with no verifiable entitlements yet still defaults to unlimited across the board (the pre-tiers behavior), so an already-paying instance never gets clamped down while waiting for its next sync. This closes a real gap for self-hosted software: since the Owner fully controls their own database, plain limit numbers cached in `app_settings` could trivially be hand-edited to unlock the paid plan; `PlanLimitService` now only trusts limits that came from a token whose signature verifies. ### Fixed
- **Mobile — page « Paramètres globaux » scrollable horizontalement, header et bottom-nav décalés** — `.theme-container` (les deux cartes de palette Kitsune/Tanuki) restait en `flex` sur une ligne non repliable alors que chaque carte passait en colonne sous 640px : le conteneur dépassait la largeur de l'écran, et le viewport glissant sur le côté entraînait la topbar sticky et la bottom-nav fixed hors de leur place. Les cartes se replient désormais (`flex-wrap`, `min-width: 0`), les pastilles de couleur aussi, et `body` coupe tout débordement résiduel avec `overflow-x: clip` (sans créer de conteneur de scroll, donc sans casser le sticky/fixed).
- Security — same flaw on the web side: `/admin/users/{id}/edit`, `/delete`, `/reset-password` and the per-employee rate actions only checked that the caller held `employees.*` *somewhere*, never the target's store or whether the target is an Owner, so a manager could view or edit an employee of another store, delete them, or reset the Owner's password to the default one. `AdminUserController` now checks the permission on one of the target's own stores (`PermissionService::requireUserAccess()`), and only an Owner can act on an Owner account.
- Security — the REST API (`/api/v1/*`) did not bound its `/{id}` routes to the resource's own store, found by the audit of 2026-10-03. `ApiPermissionMiddleware` only knows a store when the client sends a `store_id`, and `PermissionService::can(…, null)` answers "yes" as soon as any assignment grants the key anywhere, so a manager of one store could `PUT`/`DELETE` another store's shifts, availabilities, shift types or store record, read or rewrite any employee, rewrite an Owner's password hash, and read the iCal feed tokens of any account. `users`, `shifts`, `availabilities`, `stores`, `shift-types` and every `/users/{user_id}/…` route (rates, prefs, push tokens, iCal tokens) now check the permission on the resource's real store(s): new `PermissionService::hasUnrestrictedGrant()`/`requireOnAnyStore()`/`requireOnStore()`/`requireUserAccess()` and a `UserTargetGuard` shared by the per-user controllers. Only an Owner can act on an Owner account. Lists (`GET /users`, `/stores`, `/shift-types`, `/shifts`, `/availabilities`) are filtered to the caller's stores. Creating a record now needs a `store_id` the caller can write to (422 otherwise), and moving a record to another store needs the permission on the destination too.
- Security — a `POST` carrying an `id` in its JSON body turned the creation into an update of any row (every repository's `save()` upserts on `id`), bypassing the per-object checks of `PUT /{id}`; the `id` is now dropped on create in `users`, `shifts`, `availabilities`, `stores`, `shift-types` and user rates. `POST`/`PUT /users` no longer accept a raw `password_hash`: send `password` (clear text, at least 8 characters, hashed server-side; omitted on create = default password to change at first login) — changing it, or deactivating the account, revokes the user's API tokens and remember-me cookies. `GET /users` and `GET /users/{id}` no longer return `password_hash`. `PUT /stores/{id}` now rejects an unknown currency like the web form does, and iCal tokens are only issued for stores the user belongs to.
- **Photos, avatars et imports en 403 quand le serveur pointe sur la racine du dépôt** — `storage/.htaccess` refusait tout : Apache l'évalue pour l'URL d'origine `/storage/…` avant la réécriture du `.htaccess` racine vers `public/`, donc `/storage/img/…` répondait 403 sans `/public` dans l'URL. Le refus ne vise plus que ce qui existe physiquement (`app`, `backups`, `bundles`, `cache`, `logs`, `uploads` et les fichiers posés dans `storage/`) ; les URL virtuelles passent au contrôleur frontal, qui garde l'authentification, la liste blanche d'extensions et le confinement à `storage/uploads`.
- Footer — the "Report a problem" modal was permanently visible, unstyled, below the footer whenever the `feedback` bundle wasn't installed: it borrowed the `.fb-overlay`/`.fb-modal` classes whose CSS ships with that bundle. It now uses Core's own `.modal` component (`modals.css`, `openModal`/`closeModal` from `app.js`), so `report-issue.js` is gone too. The legal pages (notice, terms, licence) also threw a 500 for a logged-in user without the `feedback` bundle: they don't go through `AuthMiddleware`, so `$feedback_enabled` was never set, defaulted to `true`, and the leftover Core feedback modal built a URL to a route that didn't exist. That modal (`layout/partials/feedback-modal.php`), the footer "Give feedback" button and the `feedback_enabled` flag were bundle code left in Core and have been removed.
- Logs — the error/business log could be falsified by the client. `Log` read the user first from `$_REQUEST['auth_user']`, so `?auth_user[id]=1` in any URL that triggered an error attributed the entry to user 1, and it read the IP first from `X-Forwarded-For`/`Client-IP`, headers the client sends itself. The user now only comes from the request's `auth_user` attribute (set by `AuthMiddleware`/`ApiAuthMiddleware`), and the IP from `REMOTE_ADDR`, the same source as the login throttle.
- Security — open redirects. The shift form accepted a `?redirect_to=` link parameter checked only for "starts with `/` but not `//`", which `/\evil.example` passes while browsers read it as `//evil.example`: a manager opening a crafted link, then saving the shift, landed on the attacker's site. `AdminStoreController::addMember()` did not check its `redirect_to` at all, and the issue-report form (`SupportController`) had the same weak check. A single new `safe_redirect_path()` helper (`src/Core/helpers.php`) now only accepts an internal path (leading `/`, no `//` or backslash, no control character, no scheme or host) and falls back otherwise; it is used in all seven places (shift create/edit/conflict resolution, both form pre-fills, member addition, issue report). Legitimate destinations, all internal paths, are unchanged.
- Security — a store's currency was only checked when the store was created, not when it was edited, and `currency_symbol()` returned an unknown code as is. A user allowed to edit a store could forge a request (the field is a drop-down) to save markup as the currency, then shown unescaped on the store's profitability page to anyone opening it, the Owner included (no script could run under the CSP, but a fake link or message could). Three layers now: `StoreService::updateStore()` rejects a currency or symbol style outside the form's list (`StoreValidator::currencyErrors()`, sharing `StoreValidator::CURRENCIES` with the form); `currency_symbol()` (and so `format_currency()`) keeps only the letters and digits of an unknown code; and `analytics/store-profitability.php` escapes it. The other store fields are deliberately not revalidated on edit: existing stores have a free-text type or a locale outside the list, and blocking them would prevent any edit.
- Stores — creating or editing a store with a code already used by another store crashed with a 500 error page (the database's unique constraint threw a raw SQL error) instead of telling the user. `StoreService::createStore()`/`updateStore()` now check the code first and answer with a validation error, "The code "…" is already used by another store" (`val_store_code_taken`, fr/en/ja), for the web form and the API alike. Keeping a store's own code when editing it is still accepted.
- Security — the REST API still issued a Bearer token for the default password `0000` (or any password under 8 characters), bypassing the password change now enforced on the web: anyone knowing an employee code and a store code could get API access. `POST /api/v1/auth/login` now answers `403 PASSWORD_CHANGE_REQUIRED` instead, without creating a token or keeping a session (valid credentials, so not counted as a failed attempt by the login throttle; logged as `auth.api_login_password_change_required`). Migration `2026_10_01_000001` revokes the API tokens already issued to accounts whose password is still `0000`. While a password change is pending on the web, switching language (`/lang/…`) and the mobile/desktop view is now allowed, so an employee can read the page before changing their password.
- Deployment — a domain (or a shared host's `www/` folder, or `htdocs/Kintai/`) pointing at the repository root answered `403 Forbidden`: the root `.htaccess` was only a safety net refusing every URL outside `public/`. It now rewrites each request internally to `public/` (no redirect: the visitor's URL stays clean) so the app works wherever the server points, without touching the host's configuration. Nothing else becomes reachable — a request for `/.env`, `/src/…` or `/storage/app/database.sqlite` is looked up under `public/` and ends at the front controller (404, or the access-controlled `/storage/` route), never at the file. Without `mod_rewrite` the root now denies everything instead of exposing the repository. Because Apache then reports `SCRIPT_NAME` as `/…/public/index.php` while the URL has no `/public`, the new `kintai_normalize_script_name()` (called by `public/index.php` and `install.php`) restores the real base so generated links, redirects and the PWA scope contain no stray `/public`; direct access through `/public/` and a `DocumentRoot` on `public/` behave exactly as before. The "not installed yet" and "already installed" redirects of `index.php`/`install.php` also honour the base path instead of assuming the site root (they broke under a sub-folder).
- Language and view switch — `/lang/{locale}` and `/switch-device` sent the user back to the raw `Referer` header, set by the browser, so a link from another site bounced back to that site. Both now go through the existing `back_url()`, which only returns to a page of this site (same origin) and falls back to the home page otherwise. Changing the saved language through a hidden cross-site request was already impossible: the session cookie is `SameSite=Lax`, so it isn't sent with such requests.
- Security — the default password `0000` (given to a new account and set by an admin's password reset) stayed valid indefinitely: anyone knowing an employee code and a store code could sign in until the employee thought of changing it, and the profile page only showed a warning. A new `MustChangePasswordMiddleware` now confines a signed-in user to their profile page (plus saving the new password, logging out, the avatar and static assets) until they pick a new password of at least 8 characters. `AuthService::mustChangePassword()` flags `0000` (detected from the hash, so it also covers a session restored by the "stay signed in" cookie) and, at password sign-in, any password shorter than `PasswordPolicy::MIN_LENGTH`; it is cleared as soon as the password is changed. The `/api/v1/*` Bearer-token API and cron endpoints are unaffected. The constant `PasswordPolicy::DEFAULT_PASSWORD` replaces the scattered literals, and the profile warning (`profile_must_change_password_warning`) now explains that the rest of the app is locked.
- Installation — the command-line installer `scripts/provision.php` no longer worked. It never created the SQLite file, so it died right after writing the database config, and silently (`Application` turns error display off outside debug mode: exit code 255, no message); it would then have written `users.is_admin`, a column removed on 19/09 when roles moved to RBAC, without assigning the Owner role; it printed 8 warnings whenever an optional option was omitted; and it recorded no public URL, so password reset emails could not work. It now creates the SQLite file, assigns the Owner role like the web installer, takes `--app-url` (or `APP_URL`) for the public URL and warns when it is missing, validates its input with the web installer's rules (email, password length, URL), refuses to create a second account with an existing email under `--force`, and reports any failure with a message and exit code 1. A new CI job, `provision-smoke` (`scripts/ci/provision-smoke-test.sh`), runs it on a blank instance on every push and pull request, including its refusals and a login with the account it created; it fails on the previous script. Documented in the README (en/fr/ja).
- Sessions — changing one's language, profile or avatar copied the whole user row, password hash included, into `$_SESSION['auth_user']`, which nothing ever read (the user is reloaded from the database on every request). - Performance — the rest of the admin dashboard: the financial overview only uses the cost per month, but ran the full `storeStats()` over 180 days for each store; it now calls a new `StoreStatsServiceInterface::costByMonth()`, which runs exactly the same cost loop (same shifts, order and rates, the hourly-rate lookup now shared with `storeStats()`) and nothing else (financial widget 286 → about 110 ms). Measured locally: dashboard 544 → 404 ms (2,019 ms before #110). Results unchanged: both dashboard widgets and all 41 statistics outputs compared byte for byte, and `costByMonth()` is identical to `storeStats()['costByMonth']` on 25 store/period combinations.
- Docs — the README showed a hand-written version (`0.2.0` badge and status line) that no longer matched any release, and `SECURITY.md` said only the latest commit on `main` was supported while `main` has never had a release (every published version is an `alpha`/`beta` pre-release). README and SECURITY in en/fr/ja.
- Flash messages — anyone could craft a link that displayed the text of their choice in a genuine Kintai banner (`/profile?success=Your account is suspended, call…`): `Flash::fromQuery()` fell back to the raw query value, and several screens (bundle market, backup, update) put exception messages straight into the URL. The component now only shows messages declared by the view (or its `'default'` one) and nothing otherwise; free-text messages go through a new session one-shot store, `kintai\Core\SessionFlash`, displayed by the app layout, and the URL only carries a code. Backup and update flash parameters are validated (file name, channel, count, version). - Small fixes from the pre-V1 audit: (1) one password hashing function for the whole app, `kintai\Core\Auth\PasswordHasher` (bcrypt, cost 12) — changing one's password from the profile used cost 10, so the login's constant-time dummy check (cost 12) no longer hid the response time of those accounts; the installer and `scripts/provision.php` use it too, and a test fails if `password_hash()` reappears elsewhere; (2) new migration adding an index on `password_reset_tokens.token` for fresh installs (older instances already had one from a legacy schema, which the migration detects); (3) `StoreStatsService` no longer returns password hashes in the users list it passes to views and exports (only that column is removed; all 41 statistics outputs are otherwise identical); (4) the password reset email (subject and body) was hard-coded in French: it is now translated (fr/en/ja) and written in the recipient's own language, restoring the request language afterwards; (5) the reset form escaped its error message twice (an apostrophe would show as `&#039;`).

- Installation — **a fresh installation was impossible**: the web installer failed with `no such table: app_settings` and created no table at all, and so did `php scripts/db-migrate.php` on an empty database. `LicenseServiceProvider` runs inside the `Application` constructor, before any migration, and read the Owner's `enabled_bundles` setting from `app_settings` without tolerating a database that isn't migrated yet. Every published release since the start of the history (v0.1.0) was affected; existing instances were not, because they had been installed earlier and only ever upgraded. The provider now falls back to `config/license.php` when the table doesn't exist yet — exactly as when the setting is absent — and only database errors are tolerated. Verified in a throwaway copy on the three paths that boot the app on an empty database (`db-migrate.php`, the installer's step C, a web request), then end to end through the real `install.php` served by PHP: 46 tables, Owner account created, installation locked, and that admin can log in and open the dashboard. A new CI job (`install-smoke`, `scripts/ci/install-smoke-test.sh`) replays this fresh installation on every push and pull request, since no unit test covered it; the script refuses to run outside CI or where an installation already exists.
- Performance — the admin dashboard took about 2 s to load on a modest instance (4,500 shifts, 83 employees, 5 stores), and the time kept growing with the instance's age. `StoreStatsService::storeStats()` was requested three times per store (store comparison, financial overview, HR widget), and each call read the store's **entire** shift history twice (current and previous period) before filtering by date in PHP; the HR widget read the whole history once more. Now `storeStats()` reads only the window it needs (previous period + current period) through a new `ShiftRepositoryInterface::findByStoreBetween()` (date range in SQL on the existing `(store_id, shift_date)` index, returned without instantiating one Eloquent model per row), and its result is cached for the duration of the request; the HR widget reads only its 30-day period. Measured on the same local data: dashboard **2,019 → 544 ms**, store statistics page 315 → 134 ms. Results are unchanged: all `storeStats()` outputs (5 stores × 4 periods, with and without duration bounds) and both dashboard widgets were compared byte for byte before and after. `findByStoreBetween()` sorts explicitly by user, date and id — the order SQLite used to return implicitly — so per-employee figures keep the same order, and now the same one under MySQL.
- Password reset — the "forgot password" email contained a **relative** link (`/reset-password/<token>`), because it was built from `base()`, which only returns a path: no mail client can open it, so password reset was unusable. The link is now absolute, built from the instance's public URL, resolved by the new `PublicUrlResolver`: the `APP_URL` environment variable first, then a new Owner setting "Public URL of this instance" (`/admin/owner-settings`, validated: http(s) only, no query, credentials or fragment). It is deliberately **never** taken from the request's `Host` header, which the person asking for a reset controls (they could otherwise have a victim sent a link to their own domain and capture the token). The web installer records the address used to install as the public URL, so new instances work out of the box; existing instances without `APP_URL` show the Owner a warning until it is set, and meanwhile no email with a broken link is sent (`password_reset_no_public_url` is logged; the page stays identical so accounts still can't be enumerated). `.env.example` no longer sets `APP_URL=http://127.0.0.1`, which, copied as is, would have forced a local address into every email link.
- Release — a fresh install from a release archive reported the version literal frozen in the repository (`0.2.0`) instead of the release's own version, because `config/app.php`'s `version` is what `UpdateService::getCurrentVersion()` returns and nothing wrote it except the self-updater. With the bundle compatibility check (`kintai_core.min`), a fresh Core 0.3.0 would therefore have refused every bundle requiring 0.3.0. `release.yml` now runs the new `scripts/set-release-version.php` with the computed version before tagging (it reuses `UpdateService::setCurrentVersion()`, validates `X.Y.Z`, refuses to publish if the field is not a rewritable literal, and re-reads the file to confirm) and records it in `config/app.php` of the tagged commit. That commit is referenced only by the tag and is never pushed to the protected channel branch, so nothing changes in how branches are promoted. `docs/releasing.md` no longer says the field is informational.
- Security — the Content-Security-Policy no longer allows `'unsafe-inline'` for scripts (audit point 5): a script or an `onclick=` injected through an XSS flaw is now blocked by the browser instead of running, which is what the policy was meant to do. `SecurityHeadersMiddleware` draws a fresh nonce per request (`CspNonce`, `csp_nonce()` helper) and sends `script-src 'self' 'nonce-…'`. Every inline `<script>` in the views now carries that nonce, and the ~130 inline event attributes (`onclick`, `onchange`, `onsubmit`, `oninput`, including those passed to `Button::attrs()`) were replaced by declarative `data-*` attributes handled by one new module, `public/assets/js/modules/csp-actions.js` (`data-on-click`/`data-on-change`/`data-on-input` + `data-args`, `data-submit-on-change`, `data-submit-form`, `data-goto`, `data-stop-propagation`, a few built-ins). Confirmations that used a native `confirm()` now go through the existing `data-confirm` modal, which also accepts a `data-confirm` on a submit button attached with `form="…"`. The module refuses browser built-ins (`eval`, `setTimeout`…) and non-http(s) `data-goto`, so an injected attribute cannot become a way to run code. The two `javascript:window.close()` links are gone too. `style-src` keeps `'unsafe-inline'` (dynamic `style=` attributes). New guard `NoInlineScriptGuardTest` fails when a view reintroduces an inline handler, a `javascript:` URL or a nonce-less `<script>`; the JS module has its own tests (`tests/js/`, `node --test`, needs jsdom). **Breaking for bundles:** a bundle view still using inline handlers stops working under this policy until it is migrated; every official bundle was migrated in the same release cycle, and `docs/creating-a-bundle.md` ("Content Security Policy") documents the replacement for third-party bundles.
- Security — the minimum password length was not the same everywhere: 8 characters when resetting by e-mail, but only 4 when changing it from the profile page, so anyone could pick a weaker password than the reset flow would accept. Both now share one rule, `PasswordPolicy::MIN_LENGTH` (8, counted in characters rather than bytes), also used for the `minlength` of the profile form and the `password_too_short` message (which said 4 in fr/en/ja). Deliberately unchanged: the default `0000` given to a newly created account (an accepted decision, flagged by the existing warning until it is changed) and the current-password field of the account-deletion confirmation, which must still accept that default.
- i18n — the password-reset flow (`/forgot-password`, `/reset-password/{token}`) was the one user-facing path still written in hardcoded French: the page titles and the three error messages (password too short, mismatch, invalid or expired link) lived in `PasswordResetController`, and the reset form's title, labels, submit button and links in `auth/reset-password.php`. An English- or Japanese-speaking employee recovering their account therefore got French text. They now go through translation keys, reusing the existing ones (`forgot_password_title`, `new_password`, `confirm_password`, `new_request`, `connect`, `password_mismatch`, `reset_password_invalid_link`) plus two new ones in `lang/{fr,en,ja}.json` (`reset_password_too_short`, `reset_password_submit`) — the existing `password_too_short` key could not be reused, its text says 4 characters while this flow requires 8. A guard test fails if French literals come back in these three files.
- Tests — `PermissionMapsTest` had a blind spot: it loaded the routes of `config/routes.php` plus `src/Bundles/*/routes.php`, a folder that no longer exists now that bundles are separate repositories installed under `storage/bundles/` (absent from CI). Its glob returned nothing, so not a single bundle route (about 160 of ~380) was checked. Worse, the RBAC invariants only looked at routes that already carried `PermissionMiddleware`, so a bundle route that forgot the middleware altogether was skipped silently. The test now also loads the versioned `tests/Fixtures/bundles/*/routes.php`, and a new invariant requires every `/admin` route to go through `PermissionMiddleware` (or `OwnerOnlyMiddleware`) and every `/api/v1` route through `ApiPermissionMiddleware`, with a short documented exemption list (`/api/v1/ping`, `/api/v1/auth/login`, and the self-service Messaging API). A guard fails if the bundle routes stop being loaded, and a synthetic case proves the check detects an unprotected route. Checked by mutation: removing the middleware from one bundle route makes the test fail and name the routes. The fixtures are 1.0.0 copies, so they can lag the published bundles; the bundles' own repositories remain the place to test their latest routes. Current state: no `/admin` route outside RBAC.
- Security — a deactivated account kept working, and a changed password did not lock anyone out. `AuthService::check()` only read the session id and `user()` returned any user, active or not (`findById()` does not filter), so an employee deactivated or resigned while logged in kept their session for as long as they kept using it; only the login form and the remember-me cookie checked `is_active`. Worse, `deleteByUserId()` existed on both the remember-me and API token repositories but was never called, so a stolen "stay signed in" cookie (30 days) survived the very password change meant to neutralise it. Fixed in three parts. (1) `AuthService::user()` now refuses, and clears, the session of a missing, inactive or soft-deleted user, and `check()` goes through it. (2) Each session stores a fingerprint of the user's password hash at login; when the password changes — by the user, a reset, or an admin — every session opened before is revoked on its next request, on any device, while the one that made the change stays valid (`refreshSessionAfterPasswordChange()`). Sessions opened before this change adopt a fingerprint on their first request. (3) A new `CredentialRevoker` purges the user's remember-me cookies and API tokens; it is called on self password change, password reset by e-mail, an admin changing or resetting a password, an admin deactivating or deleting a user, and self account deletion. Covered by new tests (`AuthServiceSessionRevocationTest`, `PasswordResetRevokesCredentialsTest`, `AuthControllerCredentialRevocationTest`, `AdminUserControllerCredentialRevocationTest`) and a small PHPUnit extension that resets the session fingerprint between tests, since `$_SESSION` is shared across the whole run.
- Security — nothing stopped the web server from serving the whole repository if it was pointed at its root instead of `public/`. Checked on a development install: with the default Apache document root serving `htdocs`, `http://localhost/Kintai/.env` and `http://localhost/Kintai/storage/app/database.sqlite` answered HTTP 200 (HEAD requests only, contents not read), while the dedicated virtual host, correctly rooted at `public/`, was unaffected. The README did not say the document root had to be `public/`, and neither the repository root nor `storage/` had a `.htaccess`. A new root `.htaccess` refuses (403) every URL that does not start with `public/` — `.env`, the SQLite database, backups, logs and the source code — and disables directory listing; requests to `public/` pass through to `public/.htaccess` as before, and when the server is correctly rooted at `public/` the file is never read. It reaches existing installs through the self-update (only `storage/`, `vendor/`, `.git/`, `.env` and `config/database.local.php` are excluded from the file sync). A `storage/.htaccess` (`Require all denied`) adds a second layer for fresh installs; `.gitignore` now un-ignores it, and the app keeps serving uploads through the `/storage/{path}` route, which checks access. New README section "Web server" (en/fr/ja) states the requirement; nginx has no `.htaccess` equivalent, so its `root` must be right. Pinned by `WebRootProtectionTest` (sensitive paths refused, `public/` paths allowed, checked by mutation). If a machine was reachable this way, treat its `.env` secrets and database as exposed.
- Security — hardening of the shared `Table` component, from the pre-V1 audit. `Table::column()` inserts the HTML returned by its callback as-is (deliberately: badges, buttons, links), which leaves it to every caller to escape user-supplied data — a future free-text column that forgot to would have been a stored XSS. A review of every current `Table` in the Core and in the distributed bundles found no such case, so nothing was exploitable today. Rather than flipping the default (which would have broken the 108 columns of the 12 distributed bundles, each in its own repository, until every one was republished), `Table` gains `text()` and `sortableText()`: columns whose value is escaped automatically, so plain text needs no `htmlspecialchars()` at all. `column()`/`sortable()` stay the explicit choice for intentional HTML and now say so in their docblock. The 22 Core columns that only wrapped a value in `htmlspecialchars()` were migrated, and new `TableTest` cases pin both contracts. Also fixed a display bug found on the way: seven `Badge::make(htmlspecialchars(...))` calls escaped their label twice (`Badge` already escapes it), so a role or store named `R&D` showed up as `R&amp;D`.
- Security — login throttling was badly calibrated. The old `RateLimiterMiddleware` counted EVERY request per IP (5 per 5 minutes), successes included, and nothing targeted a specific account. In a store, where all employees share one public IP, the start-of-shift logins were rejected with a 429; meanwhile an attacker rotating IPs was never slowed down, against a default password of `0000`. A new `LoginThrottleMiddleware` now guards `POST /login` and `POST /api/v1/auth/login` and counts only FAILURES, on two independent keys: per IP (20 failures / 15 min, wide because the IP is shared) and per targeted account (10 failures / 15 min — email, or employee code + store code, normalised for case and spaces — whatever the IP). A successful login resets that account's counter. The controllers flag a failure through a request attribute (`auth_failed`) instead of the middleware guessing from the response. A blocked request gets a 429 with a `Retry-After` header, which `Application::handleException()` used to drop for every `HttpException`. Trade-off to know: anyone who knows an identifier can lock that account for the window by chaining failures; it expires by itself. Also: `POST /reset-password/{token}` had no limit at all and now uses the generic limiter, keyed by route name rather than URI so varying the token cannot dodge it; that generic limiter and the new one share an `AttemptCounter` that does its read-modify-write under a file lock (the old one read without locking, so concurrent requests could undercount). And a timing leak is closed: an unknown email, an inactive account or an unknown store code answered instantly while a real account with a wrong password paid a bcrypt check, letting an attacker tell which accounts exist; those paths now spend an equivalent bcrypt computation (measured at 0 ms before vs ~400 ms for a real check on the test machine). Behind a reverse proxy, `Request::ip()` reads `REMOTE_ADDR` only, so all clients would share the proxy's address for the per-IP counter.
- Security — two small hardenings from the pre-V1 audit. `CronController::autoValidate()` compared the `CRON_SECRET` token with `!==`; it now uses `hash_equals()` (constant-time). `AuthController::saveProfilePassword()` and `deleteAccount()` skipped the current-password check whenever the stored `password_hash` was empty; login itself never accepts an empty hash (`password_verify()` against `''` fails), so no such account can hold a session, but the skip is gone anyway and both actions now always verify the password. Covered by new tests (`AuthControllerPasswordConfirmationTest`, three cases added to `CronControllerTest`).
- Bundles — the hardcoded fallback list in `LicenseServiceProvider` (only used when `config/license.php` is missing) had drifted: it omitted `team-directory` and `notebook`, so an install without that file would have silently lost those two official bundles. - Bundles — `/admin/bundles` showed the wrong version for any bundle installed from an alpha/beta release: it displayed the `version` of the installed `bundle.json`, but a bundle's release workflow only reads that field as the "X.Y.0" baseline of the release line and computes Z itself, so a bundle installed as `1.1.8` kept showing `1.1.0`. `BundleDiscoveryService::discoverInstalled()` now reports the active version folder (`installed.json`'s `active_version`) instead, covered by a new test.
- Auth — `users.last_login_at` existed since the table's creation but was never actually written, even though logins were already tracked in `audit_log` (`auth.login`). `AuthController::login()` now updates it on every successful authentication, giving a quick per-user "last login" value without querying `audit_log`.
- RBAC — a permission marked "all stores" (`role_permissions.scope='global'`) on a role only had that effect on routes declaring that exact permission key (`PermissionMiddleware`'s `scopedStoreIds()`/`can()` path, already `permissionIsGlobalOnRole()`-aware); it had no effect at all on the many routes registered `permission: 'public'` (self-service/aggregate pages, and crucially `/storage/{path*}`, the generic route serving every uploaded file, not just photos). Those routes fall back to `PermissionMiddleware`'s generic `anyGrantedStoreIds()`, which only ever collects the `scope_id` of `scope_type='store'` assignments and never consults `getGlobalPermissionKeys()` — so a user whose assignment stayed store-scoped on their home store, but whose role granted e.g. `photos.view` globally, kept `managed_store_ids` bounded to that one store on every `'public'` route. Concretely: the photo reports list (`/admin/photos`, gated by the precise `photos.view` key) correctly showed every store's reports, but the images themselves (served via `/storage/{path*}`) silently failed to load for any store other than the user's own. A new `PermissionService::hasAnyGlobalPermissionGrant()` checks, across all of a user's assignments regardless of `scope_type`, whether any carries a system role or a role marking at least one permission as global; `PermissionMiddleware` now consults it before falling back to `anyGrantedStoreIds()`, setting `managed_store_ids` to `null` (unlimited) in that case — a user without such a grant keeps the exact same restrictive behavior as before.
- Navigation — a Manager (non-Owner) saw a different, reduced topbar/bottom-nav (the "employee" branch) as soon as they left an `/admin/*` page for one without `PermissionMiddleware` (`/employee`, `/profile`, `/docs`...), looking like two disconnected menus for the same account. `layout/app.php` derived `$isManager` from `isset($managed_store_ids)`, a request attribute only ever set by `PermissionMiddleware` — never by `AuthMiddleware`, which runs on every authenticated route. It now reads the already-shared, route-independent `auth_is_manager` (`AuthService::isManager()`, driven by the user's actual role, not the current route) that `AuthMiddleware` was already computing for exactly this purpose. `AuthMiddleware` also now shares a default `managed_store_ids` for a manager when nothing more specific has set it yet, so the topbar's single-store "employee report" shortcut link stays consistent too — `PermissionMiddleware` still overrides it with its own finer per-permission scope on every route it covers.

- **Breaking (API)**: `/api/v1/*` now enforces RBAC authorization — until now, any authenticated token (including a plain employee's) could read and modify every resource of every store. ### Fixed
- The installer no longer fails with "Database file at path [...] does not exist." when `storage/app/database.sqlite` is missing (e.g. after an incomplete or deleted previous install) — the file and its directory are now created automatically before the framework boots.

- **Security:** the Messaging and DailyReport bundles' `/api/v1/*` routes were registered without `ApiAuthMiddleware`, unlike every other `/api/v1/*` endpoint — they were reachable without a Bearer token even though their controllers assumed an authenticated `auth_user`. Both bundles' `routes.php` now wrap their API routes in the same protected group as the core API.
- **Critical:** shift swap requests were completely broken — creating, accepting, or refusing a swap wrote/read the columns `target_id`/`peer_accepted_at`, which don't exist in the `shift_swap_requests` table (real columns: `target_user_id`/`accepted_at`). Every attempt to create a swap threw a SQL error, and swap statistics silently under-counted the target side. Fixed in `EmployeeController`, `AdminSwapController`, the swap views, the dashboard, and `StoreStatsService`.
- `DELETE /api/v1/notifications/{id}` marked the notification as read instead of deleting it. `NotificationRepositoryInterface` gained a `delete()` method and the endpoint now actually deletes.
- `scripts/db-migrate.php --dry-run` was documented but never implemented — the script read no CLI arguments at all. It now lists pending migrations without applying them.
- `scripts/docker-setup.php` hashed the admin password with a different bcrypt cost than `install.php`/`provision.php`; aligned to cost 12.

- **Critical:** disabling a bundle from `/admin/bundles` crashed the dashboard and sidebar with a 500 ("Route [...] not defined") for every user whose store still had the corresponding `store_features` slug checked (and unconditionally for Owner accounts, since the per-store toggle is bypassed for them). The sidebar, bottom nav, and both dashboards generated `route_url()` links to bundle-owned routes based only on the per-store toggle, never on whether the bundle itself was still enabled instance-wide. Added `FeatureManager::STORE_FEATURE_BUNDLE_MAP` (single source of truth for the store-feature-slug → bundle-slug mapping, replacing `AdminStoreController`'s private copy) plus two helpers, `bundle_enabled()`/`feat_bundle()`, now consulted everywhere a bundle-gated route is linked: the three independent `$feat()` closures (`app.php`, `dashboard/index.php`, `employee/dashboard.php`), the Owner/Manager branches of `_sidebar.php` (the Owner branch previously had no bundle check at all), `_bottomnav.php` (hrefs are now lazy closures, since the nav-item pool array previously called `route_url()` unconditionally for every item before the per-item visibility filter ran), the "feedbacks" settings tab, and the "request a swap" button on the three shift-calendar/timeline views.
